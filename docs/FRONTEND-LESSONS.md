# Frontend Lessons

Background and incident history behind the frontend rules in `src/CLAUDE.md`, kept here so the
rules there stay short. Read it when changing `EmailHtmlFrame`, the sanitizer, or a settings panel.

## Component Identity & Remounts

- **Never define a component inside another component.** A nested definition gets a fresh function identity on every render, React sees a different element *type*, and it unmounts + remounts the whole subtree instead of reconciling it. Hoist it to module scope and pass what it needs as props. Enforced by `lint/correctness/noNestedComponentDefinitions` (enabled in `biome.json`) — it was silent before because it belongs to Biome's `react` domain, which `"recommended": true` alone does not switch on.
- The symptom is never a crash, which is why this shipped twice: state that React does *not* own is silently destroyed on every parent render. That means scroll position, focus and caret, CSS transitions mid-flight, and the height a user dragged a `<textarea>` to. `useState` values survive (they live in the parent), so the panel looks "almost right" and the bug reads as flicker.
- Both incidents were the same `Shell` wrapper (modal vs. embedded chrome) defined inside the settings panel body: `AiSettings` (scroll jumped to top on every context-window spinner click) and `ClassificationSettings` (window flickering and the intents/topics textareas snapping back to `rows={4}`, reported on Windows during a large initial Gmail sync). Regression tests: `AiSettings.scroll.test.tsx`, `ClassificationSettings.scroll.test.tsx` — they assert the structural property directly by capturing a DOM node, forcing a parent re-render, and requiring the *same* node back.
- What turns this from a latent defect into a user-visible one is render frequency, so the panels that host long-lived editable state are the exposed ones. Anything rendered under `App` re-renders on every `sync-progress` batch event (one per synced chunk — `services/emails/sync.rs`), so during a first sync a remount-on-render bug fires continuously.

## Email HTML Rendering

- Email HTML renders inside a sandboxed `<iframe srcdoc>` (`sandbox="allow-scripts"`, no `allow-same-origin`, no `allow-popups`: every link goes through the bridge) via `src/components/shared/EmailHtmlFrame.tsx`. The null-origin iframe gives the email its own document, which (a) lets modern email templates work — ticket cut-outs, responsive `<style>` media queries, hero-image sizing, `display:none`/`visibility:hidden` for mobile-only blocks — without leaking CSS into the app's Tailwind layer, (b) prevents any script that somehow survives DOMPurify from touching the parent DOM, cookies, or storage, and (c) blocks the iframe from navigating the top window.
- A small trusted bridge script injected into the srcdoc handles auto-height (`ResizeObserver` → `postMessage({type:'height'})`), link interception (`postMessage({type:'link', href})` → parent routes via `getSafeExternalUrl` + confirmation modal + `plugin-shell.open`), and search highlighting (parent posts the query, iframe walks text nodes and wraps `<mark>`s).
- **Auto-height must measure `document.body.scrollHeight`, never `document.documentElement.scrollHeight`.** The root element's `scrollHeight` floors to the viewport height, and inside the frame the viewport equals the height the parent just set on the iframe — so feeding it back creates a one-way ratchet that can only grow (the v0.5.0 runaway-height bug: a ~20,654px email measured 23,622px and climbed). The body shrink-wraps its content, so its `scrollHeight` reflects the true height and stays stable across re-measurements. `EmailHtmlFrame.height.test.ts` evals the real `BRIDGE_SCRIPT` under jsdom with the two scroll heights stubbed apart and asserts the posted height is the body value — keep it green.
- **CSP differs between dev and production — never loosen or bypass it to make something work locally.** Tauri's dev server (Vite HMR) relaxes the configured CSP with `'unsafe-inline'`/dev-server allowances, so inline `<script>`/`<style>` that runs fine in `make dev` can be silently blocked in a release build. A `srcdoc` iframe inherits the parent document's CSP, so the injected bridge script is governed by the app `script-src` in `src-tauri/tauri.conf.json`. This is exactly how the v0.5.0 "body collapses to ~40px" bug happened: production CSP blocked the inline bridge, no `height` message was ever posted, and the iframe stayed at its 40px initial height. Do **not** "fix" CSP failures by setting `"csp": null`, adding `'unsafe-inline'` to `script-src`, or otherwise weakening the policy. The only acceptable fix for a required inline script is to allowlist it by its **sha256 hash** in `script-src` (base config only — the per-platform overlays under `src-tauri/` merge on top and inherit it). `EmailHtmlFrame.csp.test.ts` recomputes the hash from `BRIDGE_SCRIPT` and asserts it is present, so any edit to the bridge script forces the CSP to be updated in lockstep — keep that test green rather than deleting or skipping it. When debugging WebView rendering, always reproduce in a release/`tauri build` context (not just dev), since dev's relaxed CSP hides production-only failures.
- **The frame is pinned to the light scheme.** The webview (and so the srcdoc iframe) inherits the OS appearance, but the reading pane is light-only. With macOS in dark mode, a newsletter's `@media (prefers-color-scheme: dark)` rules turned its text `#FFFFFF !important` while its dark background never applied — white text on the white pane. The frame now declares `<meta name="color-scheme" content="light">` + `:root { color-scheme: light only; }`, and the bridge's `dropDarkSchemeRules` removes dark-scheme media conditions from the email's parsed stylesheets via the CSSOM (engine-independent — WebKit does not reliably propagate the scheme into iframes). `EmailHtmlFrame.colorScheme.test.ts` covers it. On the app's own dark theme the frame follows `src/lib/emailScheme.ts` (pure planner, `planEmailScheme`): a message with its own dark-scheme rules gets them forced on (`<html data-dark-rules="force">`, the bridge rewrites the media list to `all`), a plain message or a light design is adapted with a hue-preserving luminance inversion on `body` that images undo (`frameSchemeCss`), and a design that is already dark is left on a dark canvas. The planner reads the message as received (`schemeSource`): sanitizing drops `<body>` and its `bgcolor`, often the page's only background, and a translucent background counts as the tint it gives the white page. `EmailHtmlFrame.darkTheme.test.tsx` and the colour-scheme test cover the three plans. Changing `BRIDGE_SCRIPT` changes its CSP hash — update `tauri.conf.json` (the csp test says which value).
- `sanitizeEmailHtml` / `sanitizeEmailHtmlFull` keep `<style>` tags (`ADD_TAGS: ['style']` plus `FORCE_BODY: true` so DOMPurify doesn't drop them into a stripped `<head>`) and most inline-style properties. `behavior` / `-ms-behavior` are still blocked because they're the historical CSS-as-script vector. `expression(...)`, `javascript:` URIs, and `url(data:image/svg+xml…)` / `url(data:text/html…)` remain rejected at the value level. CSS declarations are split via a paren-aware splitter so semicolons inside `url(data:image/...;base64,...)` don't bisect a single declaration into evading fragments.
- Remote content gating still applies. `sanitizeEmailHtmlFull(html, allowRemoteContent)` strips remote `src`/`poster`/`srcset` from **every** element that fetches on its own — `<img>`, `<source>`, `<video>`, `<audio>`, `<track>` (the `REMOTE_FETCHING_TAGS` set) — and rejects remote `url(...)` inside inline `style` attributes when `allowRemoteContent` is false. Gating only `<img>`/`<source>` was a real read-receipt hole: DOMPurify's `html` profile passes `<video>`/`<audio>` through, and `<video poster>` fetches on render with no user interaction. **When adding a tag to the allowed set, check whether it can fetch a URL and add it to `REMOTE_FETCHING_TAGS` if so.** The legacy `background` attribute is stripped too. CSS inside `<style>` blocks is not rewritten; instead, with remote content off, `EmailHtmlFrame` (`allowRemoteContent={false}`) stamps a per-frame `<meta http-equiv="Content-Security-Policy" content="img-src data: blob: cid:">` into the srcdoc — a frame policy stacks on the inherited app CSP, whose `img-src` allows `https:` — and a remote `url()` in a `<style>` block only raises `hasBlockedImages` so the banner shows. `EmailHtmlFrame.remoteContent.test.tsx` covers it.
- Inline images use `cid:` Content-ID references to MIME attachment parts. The Gmail API returns these as base64-encoded parts with `Content-ID` headers. Extract during sync and convert to `data:` URIs in the HTML body.
- Plain text emails (no HTML part) need proper conversion: `[image_url]<link>` is Outlook's format for linked images. Convert to `<img>` / `<a>` tags. Use `white-space:pre-wrap` instead of `<pre>` for better flow.

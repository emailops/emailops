# services/emails

## What this module owns

All business logic for email read/write operations that cross the provider boundary or require multi-step coordination:

- **sync.rs** — full-account sync (fetch from provider → upsert to DB → trigger embeddings/classification). A sync opens with the UIDVALIDITY check and the retry of pending read-state pushes (see `uid_validity.rs`, `mailbox_state.rs`). The fetch passes are insert-only, so what the user does to stored mail in the provider's own client is invisible to them; `state_refresh.rs` closes that for recent IMAP/Outlook mail, `history_refresh.rs` for Gmail, and the Spam pass closes it both ways for Spam. **Out of Spam:** `reconcile_spam_moves` diffs recent local spam against the Spam listing (widest of `SPAM_RECONCILE_WINDOWS_SECS` whose listing fits under `MAX_SPAM_RECONCILE_LISTING`, so a busy folder reconciles a shorter stretch rather than nothing) and locates each row missing from it via `EmailProvider::locate_message`. Gmail keeps the message's id; IMAP and Graph re-key the move, so the row is re-keyed with `migrate_email_id` (tags, body and embeddings travel with it) or soft-deleted when that id is already stored. **Into Spam:** `ingest_mailbox_refs` re-files ids the listing reports that are already stored under another mailbox (Gmail), and hides older copies of the same `Message-ID` when the Spam row arrives under a new id (IMAP/Graph). Runs at most once per `SPAM_RECONCILE_INTERVAL_SECS` per account; messages the provider deleted forever are kept locally and remembered so they are asked about once
- **drafts.rs** — AI reply/new-email draft generation. Pure planner `plan_reply_prompt` splits the prompt into a stable prefix (template + persona/style, KV-cache anchor) and a per-draft suffix: the thread cut at the answered message (`thread_up_to`), cleaned bodies fitted by `allocate_thread_budget`, the user's past messages to the same correspondent as voice samples (`build_style_context`), RAG precedents and the user's instruction. The executor calls `AiService::complete_with_prefix`.
- **send.rs** — send reply / new email through the provider's SMTP or API; after the provider accepts, inserts an optimistic local Sent row (via `optimistic.rs`) so the message shows in the thread/Sent views immediately, and for Gmail spawns a background authoritative `get_message` refresh
- **optimistic.rs** — pure planner for the optimistic Sent row: provider-keyed permanent row when the send returned a canonical id (Gmail), synthetic `local-sent-<uuid>` row with `pending_sync = 1` otherwise (Outlook/IMAP)
- **reconcile.rs** — pure planner + thin executor that matches `pending_sync = 1` rows against provider-ingested Sent copies (exact RFC Message-ID for IMAP, conservative subject/recipients/time heuristic for Outlook), deletes the synthetic row, and moves the incoming row into the local thread when thread ids diverged. Hooked after both `insert_emails_batch` sites in sync.rs and after each insert of the failed-download retry; a 24h stale sweep, run after every ingest pass (extra mailboxes included), un-flags rows that never matched
- **mailbox_state.rs** — read/unread and delete, plus their provider write-back (Gmail, IMAP, Outlook — `provider_supports_mailbox_writes`). Read state is local-first with a best-effort push (reading mail must work offline): the row is marked pending (`emails.read_push_pending_since`, V029) in the same statement, cleared when the provider has the change, and `retry_pending_read_pushes` — pure planner `plan_read_push_retries` — pushes what is still pending at the start of every sync (capped, gives up after a week). Delete is provider-first (move to Trash) so a refused push leaves the message visible instead of diverging silently; a provider answering "no such message" counts as deleted
- **state_refresh.rs** — server-to-local refresh of mail that is already stored, for providers implementing `fetch_message_states` (IMAP, Outlook). Pure planner `plan_state_refresh` diffs stored rows against the provider's answer; the executor applies read-state changes and follows vanished messages with `locate_message` (re-key in place, or soft-delete). Bounded: last 30 days, 200 rows and 25 lookups per pass, once per 2 minutes. A row with a pending local push is never touched; otherwise the server wins. Runs at the end of `sync_extra_mailboxes`. It is the one entry point and owns the throttle: a provider with a change log is handed to `history_refresh.rs` first and never polled
- **history_refresh.rs** — the same refresh for Gmail, from its History API. Pure planner `plan_history_changes` folds a page of label changes and deletions onto the stored rows (several changes to one message collapse in order; unknown ids are ignored) and maps the result through `sync::gmail::mailbox_from_labels`: `UNREAD` is the read state, `TRASH` files the row under `trash`, a permanent delete soft-deletes it, and archiving or user labels change nothing (there is no archive mailbox). The executor keeps a per-account cursor in preferences (`mailbox_history_cursor:<account>`): seeded from the mailbox's current position on the first run, moved only past fully applied pages, at most 5 pages per pass. A page that had to skip a row with a pending local push is replayed later. When Gmail no longer keeps the log back to the cursor, the recent stored rows (same 30 days / 200 rows) are checked against their current labels (`plan_label_snapshot`) and the cursor is reseeded only once all of them were checked. Spam is left to the Spam pass
- **uid_validity.rs** — IMAP UIDVALIDITY. `reconcile_uid_validity` runs first in every sync and is fatal on failure: it compares each mailbox's value with `folder_uid_validity` (V027) and, on a change, re-keys the stored rows onto their messages' new UIDs (pure planner `plan_uid_rekey`: Message-ID, then arrival time), removes rows nothing matches and reopens the mailbox's sync windows (`sync::reopen_mailbox_sync`)
- **compose.rs** — draft compose/save/send/delete, the sync-time provider draft reconciliation (`pull_provider_drafts`: one `sync::draft_plan::plan_draft_sync` decision per draft — pull, push, re-create, prune or keep), and the on-demand pull behind the UI triggers (`refresh_provider_drafts`, throttled per account by `DRAFT_REFRESH_COOLDOWN_SECS` so opening the Drafts screen and then a draft costs one listing call)
  - A composer save marks the draft dirty (`drafts.dirty`, the count of saves since the last push) in the same write as the text. **A dirty draft is never pruned or overwritten**: the sync pushes it, it wins when the provider copy changed too, and it is created again upstream when that copy was sent or deleted from another device (also on a save whose update the provider answers with not-found). Only clean drafts are pruned or replaced by a pull. The guards are repeated in the SQL (`upsert_provider_draft`, `prune_provider_drafts`, `mark_draft_pushed`) so a save racing the sync is covered too. `db.save_draft` (chat draft tool) does not mark dirty, so AI-generated drafts stay local until the user saves them in the composer
- **provider.rs** — thin wrappers that map provider-neutral `Email` to provider-specific send payloads
- **redownload.rs** — re-fetch emails whose body is empty (e.g. after a failed initial sync)
- **events.rs** — Tauri event emission helpers (`emit_sync_progress`, `emit_sync_complete`)
- **mod.rs** — re-exports the public surface

## Dependencies

- `db/emails` — all SQL queries (reads via `db.reader()`, writes via `db.connection()`)
- `sync/provider.rs` — `EmailProvider` trait for Gmail/IMAP/Fake
- `ai/provider.rs` — `AIProvider` trait for draft generation
- `services/task_queue` — heavy work (sync, draft gen) is submitted here, not awaited inline
- `services/logger` — log seam for output panel events
- `services/events` — UI event seam (`sync-progress`); `None` AppHandle still emits via the seam

## Public surface

- `sync_account(db, account_id, app_data_dir, app: Option<AppHandle>, ai_background, abort_flags, sync_locks) -> Result<()>` — `app=None` (CLI) routes progress through the events seam and skips AppHandle-bound follow-ups (AI tasks, attachments)
- `sync_account_with_contention(..., contention)` — same, but `SyncContention::Wait` queues behind the in-flight sync (capped at 5 min) instead of skipping. For callers that have just invalidated the running sync's settings, where skipping would leave the account on the settings the user replaced
- `request_sync_abort(abort_flags, account_id)` — ask the in-flight sync to stop at its next batch boundary (already-downloaded emails are kept). Consumed by the run that observes it, so a request raised while nothing is running cannot abort a later sync
- `request_extra_mailbox_backfill_reset(db, account_id)` — queue a drop of the per-mailbox "swept back to the floor" markers and cursors. Called when the sync range widens; the forward watermarks are left alone. The next sync applies it under the account lock, so the run being retired (which still holds the old floor, and never checks the abort flag during its extra-mailbox phase) cannot write its stale markers back over it
- `generate_draft(db, email_id, account_id, app, ai_queue) -> Result<String>`
- `send_reply(db, email_id, body, from_account_id, to, cc, app) -> Result<String>` (returns sending account id for a post-send sync)
- `send_new_email(db, account_id, to, cc, subject, body, attachments, app) -> Result<String>` (returns sending account id for a post-send sync)
- `redownload_email(db, email_id, app_data_dir, app) -> Result<Email>` / `redownload_email_with_provider(db, email_id, provider)` — re-fetch the content; mailbox, sent flag, read state and triage are kept from the stored row
- `mark_as_read(db, email_id, app) -> Result<()>` / `delete_email(db, email_id, app) -> Result<()>` — command entry points that resolve the provider themselves; the `*_with_provider` variants take an injected provider (`None` = local-only) and are what tests drive

## What should NOT live here

- SQL queries — those go in `db/emails/`
- Provider authentication / token refresh — that is `services/accounts`
- Scheduling decisions (when to sync) — that is `services/sync_scheduler`
- Classification / tagging — that is `services/classification`

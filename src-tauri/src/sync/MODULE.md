# sync

## What this module owns

Provider-specific email synchronisation adapters plus the shared `EmailProvider` trait.

- **provider.rs** — `EmailProvider` trait + `FakeEmailProvider` test double. The trait defines the minimal surface all sync paths share: `list_messages`, `get_message`, `send_reply`, `send_new_email`, `download_attachment`, plus default-empty folder methods (`list_folders`, `list_folder_messages`) that only the IMAP adapter implements — Gmail/Outlook silently skip custom-folder sync. Folder *management* (`create_folder`, `rename_folder`, `delete_folder`, `move_message` with a `MoveTarget`) defaults to a typed "unsupported" error; only IMAP overrides it, and `services/emails/folders.rs` owns the orchestration (provider-first, then in-place local migration). `locate_message(id, message_id_header)` reports where a message sits now, as a `MessageLocation { id, mailbox }` (`Ok(None)` = the provider no longer has it); all three adapters implement it for the spam reconciliation. Gmail reads the labels (`format=minimal`, 404 → `None`) and returns the same id; IMAP checks the UID in its own folder and otherwise re-finds the message by `HEADER Message-ID` in INBOX/Trash; Outlook queries `internetMessageId` in `inbox`/`deleteditems`/`archive`/`junkemail` (Graph's `archive` maps to the app's `archive` mailbox). IMAP also searches up to `MAX_LOCATE_FOLDERS` custom folders, so a message filed out of Spam into a user folder is found as `folder:<path>`. The last two return the message's **new** id, because a move re-keys it there. Sends return a best-effort `SentMessageMeta` (Gmail: provider `id`/`threadId` from the send response; IMAP: the lettre-generated RFC Message-ID; Outlook: empty — Graph returns 202 with no body) so `services/emails` can insert an optimistic local Sent row. Mailbox-state writes: `set_read_state`, `set_starred` (Gmail `STARRED`, Graph `flag`, IMAP `\Flagged`), `trash_message` and `archive_message` (Gmail removes `INBOX` and keeps the id; Graph moves to `archive` and IMAP to the `\Archive` folder — `folder_plan::resolve_archive_folder` — both re-keying, so it returns a `MessageLocation`; IMAP without an archive folder is `AppError::NoArchiveFolder`). Its inverse is `move_message(MoveTarget::Inbox)`, which Gmail (add `INBOX`) and Outlook (move to `inbox`) implement for that target only. `RemoteMessageState::Present` carries `is_starred: Option<bool>` (`None` = not reported). The fake's `set_send_meta` simulates each shape; `set_folders` simulates a server `LIST` response; folder ops mutate its state and are recorded for assertions (`folder_ops`, `set_move_result`).
  Mailbox state goes both ways through the trait. **Writes:** `set_read_state` and `trash_message(id, message_id_header)` are implemented by all three adapters (`provider_supports_mailbox_writes`); `trash_message` always means "move to Trash", never a permanent delete, and `AppError::NotFound` means the provider no longer has the id. **Reads:** `fetch_message_states(ids)` reports `Present { is_read }` / `Missing` for stored messages, and only for ids it could actually check — IMAP and Outlook implement it, Gmail answers `None` because it is followed through its change log instead: `history_cursor()` (the log's current position; `None` = no change log), `list_history(cursor, page_token)` (a `HistoryPage` of `MessageChange`s in order plus the cursor to resume from, or `HistoryListing::CursorExpired`) and `fetch_message_labels(ids)` (`RemoteLabels`, for the bounded check that replaces an expired cursor). **UIDVALIDITY (IMAP only):** `folder_uid_validities()` reports each stored mailbox's value plus the id prefix of its messages, and `list_mailbox_identities(mailbox)` lists a mailbox as `(id, Message-ID, arrival time)` for the re-key after a change. The fake models all of it: `fail_mailbox_writes` / `fail_mailbox_writes_as_not_found` / `restore_mailbox_writes`, `report_message_states` (opt-in) with `set_remote_read` / `remove_message` / `relocate_message` / `make_state_unverifiable`, `set_folder_uid_validity` / `fail_identity_listing`, and a Gmail-like change log: `enable_history`, `record_history`, `expire_history`, `set_history_page_size`, `fail_history_listing`, `fail_label_fetch`.
- **folder_plan.rs** — pure planner for IMAP `LIST` responses: modified UTF-7 decoding *and encoding*, SPECIAL-USE (RFC 6154) role mapping with a localized name-candidate fallback (en/de/es/fr — "Gesendete Objekte", "Papierkorb", …), and classification of the remaining selectable folders as custom folders. Also owns the pure folder-management helpers: `validate_folder_name`, `compose_folder_path` (INBOX-nesting heuristic), `rename_sibling_path`. No I/O; `imap.rs` resolves Sent/Spam/Trash through it (including the sent-copy APPEND target) and `services/emails/sync.rs` persists its plan into the `folders` table.
- **draft_plan.rs** — pure planner for the draft pull pass. `plan_draft_fetches(listed, known)` splits a provider's cheap draft listing into `to_fetch` (content actually changed) and `present_ids` (everything upstream, the prune keep-list). Providers report a per-draft `change_token`; Gmail uses `draft.message.id`, which it re-mints on every save, so an unchanged id proves the content is untouched. No I/O.
- **gmail.rs** — Gmail REST API adapter (OAuth 2, incremental sync via `after:` filter, attachment handling, category mapping). `mailbox_from_labels` is the one mapping from labels to a local mailbox (`TRASH` → trash, `SPAM` → spam, `SENT` without `INBOX` → sent, anything else — archived mail included — → inbox). Changes made in Gmail's own clients are read with `users.history.list` (`labelAdded`/`labelRemoved`/`messageDeleted` only, 100 records a page; a 404 for a start id Gmail no longer keeps becomes `CursorExpired`), the starting position with `users.getProfile`, and current labels with a batch of `format=minimal` gets (50 per batch). All of it goes through the same retry and rate-limit gate as every other Gmail request
- **outlook.rs** — Microsoft Graph API adapter (OAuth 2, delta sync, category mapping). Attachments that do not fit in one request (any file of 3 MB or more, or files that together reach 3 MB) take the draft route, for new mail, replies, and draft create/update alike: the message is created as a draft without attachments (`POST /me/messages`, or `createReply` for a reply), each attachment is added on its own — `POST …/attachments` for a small one, an upload session for a large one (`createUploadSession`, then `PUT`s of 2,949,120-byte ranges with `Content-Range` to the pre-authenticated `uploadUrl`, no `Authorization` header; 200 + `nextExpectedRanges` while more is expected, 201 at the end) — and the draft is sent with `POST …/send`. A failed range is re-sent up to five times; a session that cannot be completed is cancelled (`DELETE uploadUrl`) and the draft this client created is removed. A failed final send keeps the draft (it may have been sent; it is never repeated). An update replaces the draft's attachments (list, delete, add). Everything under the limits keeps the single request it always used. Read state is `PATCH /me/messages/{id}` `isRead`, delete is `POST …/move` to `deleteditems`, and the state refresh is a `$batch` of `$select=id,isRead` GETs. A 404 from Graph is returned as `AppError::NotFound` (a moved message is re-keyed, so its old id 404s)
- **imap.rs** — IMAP/SMTP adapter (native-TLS, IDLE for push notifications, SMTP for send). Message ids encode their source folder: `{account}::{uid}` (INBOX), `SENT::`/`SPAM::`/`TRASH::` sub-prefixes (canonical roles, frozen for backward compat), and `FOLDER::{b64url(server_path)}::{uid}` for custom folders (base64url shields `::` and non-ASCII in folder paths; `folder_email_id_prefix` exposes the shared prefix for rename migrations). Folder management maps to `CREATE`/`RENAME`/`DELETE`, and `move_message` uses `UID MOVE` when the capability is advertised (else `COPY` + `\Deleted` + `UID EXPUNGE`/`EXPUNGE`), then resolves the message's new UID in the target folder via `UID SEARCH HEADER Message-ID`. Read state is `UID STORE ±FLAGS.SILENT (\Seen)`; delete moves the message to the Trash folder through the same move path after checking that the UID still carries the expected Message-ID.
- **imap_search.rs** — lenient wrappers around the `imap` crate, generic over the stream so they are tested against a scripted server: `uid_search`, `select`, `uid_copy`, the `BODY.PEEK[]` fetches, `uid_store_seen`, `uid_fetch_flags` (+ pure `parse_flags_response`), `examine_uid_validity` (+ pure `parse_uid_validity`) and `uid_fetch_identities`. The module docs explain, per command, why it bypasses or retries the crate's typed parser.
- **outlook_upload.rs** — pure planner for the above: `plan_attachments` (inline vs upload session per file, single request vs draft route, `InvalidInput` naming a file over Graph's 150 MB before anything is sent), `EncodedContent` (byte ranges decoded straight from the base64 text, so a large file is not held decoded next to its encoded copy), `content_range`, `next_offset`, `upload_session_payload`.
- **oauth.rs** — shared OAuth 2 helpers (PKCE flow, token refresh, callback listener; a callback carrying `error=` with our `state` ends the wait immediately, and the blocking listener runs on `spawn_blocking`)
- **http_client.rs** — `provider_http_client(timeout)`: every provider/OAuth `reqwest::Client` gets a 10 s connect timeout plus a whole-request timeout (`API_REQUEST_TIMEOUT` 120 s; `MAIL_REQUEST_TIMEOUT` 600 s for the mail clients, which share one client with attachment sends/downloads)
- **http_retry.rs** — retry classification for the calendar clients plus `RetryPolicy`: sends, draft/event creates, cancels and RSVPs use `NoRetryAfterSend` (retried only on 429 or a failed connect), so a 5xx never duplicates them; the Gmail/Graph mail clients apply the same policy
- **calendar_provider.rs** — `CalendarProvider` trait + `FakeCalendarProvider`. One method (`list_events(window)`) returning provider-expanded recurrence instances; v1 has no sync tokens (full-window fetch each cycle — see `services/calendar/sync.rs`).
- **gmail_calendar.rs** — Google Calendar v3 adapter (`events.list` with `singleEvents=true`; pure `parse_google_event`)
- **outlook_calendar.rs** — Graph calendar adapter (`/me/calendarView` with `Prefer: outlook.timezone="UTC"`; pure `parse_graph_event`)
- **mod.rs** — re-exports

## Key design decisions

- **`EmailProvider` is `async` and `Send + Sync`.** Fakes can be constructed without a network; real impls hit the provider API.
- **Incremental sync is the norm.** Every real adapter queries with a `since_timestamp` so a second sync on an up-to-date mailbox returns 0 messages, not 50 000. Drafts follow the same rule via `list_drafts(known_change_tokens)`: Gmail's listing is cheap but its per-draft read is not, so a steady-state pull is one `drafts.list` and zero `drafts.get`. Adapters must still return *every* upstream draft id in `present_ids` — it is the keep-list for `prune_provider_drafts`, so a truncated list deletes local drafts. Both adapters therefore paginate their draft listing to exhaustion (`nextPageToken` / `@odata.nextLink`), and both error out at `MAX_DRAFT_PAGES` rather than returning a truncated list. Graph returns full bodies in the listing, so Outlook reports every draft as changed and tracks no token.
- **The IMAP inbox pass piggy-backs a Sent listing** that ignores the caller's window (a thread's first message is often one the user sent, older than anything in INBOX) but *not* the account's own floor: `ImapClient::with_sync_from` binds `Account::sync_from_timestamp` so an account set to "last 7 days" no longer pulls years of sent mail. `emails_exist_batch` dedupes the overlap.
- **IMAP is blocking.** The IMAP crate uses a blocking API; calls run in `spawn_blocking`. IDLE notifications arrive via a `mpsc::Sender<bool>` so the async sync path can await them.

## Dependencies

- `services/accounts` — OAuth token retrieval / refresh
- `services/keychain` — keychain seam for token persistence
- `db/emails` — upsert helpers called after a successful fetch
- `models/` — `Email`, `EmailAttachment`, `Account` types

## What should NOT live here

- Business logic (draft generation, classification) — those are in `services/`
- DB schema — that is `src-tauri/migrations/`
- Sync scheduling (when to sync) — that is `services/sync_scheduler`
